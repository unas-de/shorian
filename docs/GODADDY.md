# التشغيل على GoDaddy

لم يُنفّذ نشر على GoDaddy بعد: نوع الخطة والدومين وإمكانية الوصول إلى الخادم غير معروفة. ملفات VPS المجهزة في `deploy/godaddy` لا تثبت تشغيل الموقع أو إصدار شهادة HTTPS.

## اختر المسار حسب المنتج الموجود

- **VPS / Dedicated مع SSH وصلاحية sudo:** المسار المجهز أدناه؛ Node 24، عملية واحدة، قرص دائم، systemd وCaddy للـHTTPS.
- **Web Hosting/cPanel مشتركة:** يلزم أولًا فحص توفر تشغيل تطبيق Node 24 وعملية دائمة وقرص وذاكرة كافيين ودعم reverse proxy من مقدم الخدمة. مجرد وجود cPanel أو SSH لا يثبت هذا الدعم. لا ترفع التطبيق إلى public_html قبل التأكد. إن لم تدعم الخطة تشغيل Node فالحل VPS، أو استضافة التطبيق خارجيًا مع بقاء الدومين لدى GoDaddy.
- **Domain فقط / Managed WordPress / Website Builder:** الدومين لا يشغّل خادم Next.js، وWordPress ليس runtime لهذا التطبيق. يمكن ربط الدومين بخادم التطبيق عبر DNS دون نقل تسجيل الدومين.

لا تشترِ ترقية أو تغيّر DNS قبل التأكد من نوع الخطة وتكلفتها. لا ترسل كلمة مرور الحساب أو مفتاح SSH الخاص في المحادثة. نحتاج لاحقًا اسم النطاق والوصول المصرح به إلى الخادم عبر وسيلة آمنة.

## مواصفات مسار VPS المجهز

Linux مع systemd (مثل Ubuntu 24.04)، Node.js 24، وقرص دائم. يوصى بذاكرة 2 GiB على الأقل للتقييم، و4 GiB للبناء على الخادم؛ لم يُجرَ اختبار أحمال إنتاجية. الخادم المحلي وصل إلى نحو 417 MiB قبل البناء أو الأحمال. تظل قاعدة PGlite في عملية واحدة؛ لا PM2 cluster ولا عدة نسخ للتطبيق.

## تنفيذ للمسؤول على الخادم بعد توفير الوصول

هذه الخطوات إرشادات، ولم تُنفّذ على حساب GoDaddy:

1. تثبيت Node 24 من مصدر موثوق مع تحقق التنزيل، وGit وCaddy من حزم موثوقة. التأكد من `node --version` وأن node متاح في `/usr/local/bin` أو `/usr/bin`.
2. إنشاء مستخدم خدمة بدون صلاحيات root باسم `shorian`. وضع checkout في `/opt/shorian/app` من مستودع `unas-de/shorian` وفرع `deploy/shorian-demo`. للمستودعات الخاصة استخدم آلية GitHub مصرحًا بها أو مفتاح نشر محدود القراءة؛ لا تضع token في URL أو Git config.
3. إنشاء `/var/lib/shorian` بملكية `shorian:shorian` ووضع 0700. ربط `/opt/shorian/app/.data` به **فقط إن لم يكن المسار موجودًا**. إن وُجدت `.data` سابقة فتوقف واحفظ نسخة موثقة وانقلها مع الحفاظ على البيانات؛ لا تستخدم حذفًا أو استبدالًا تلقائيًا.
4. من مجلد التطبيق والخدمة متوقفة: `npm ci --include=dev --no-audit --no-fund` ثم `npm run build`. لا ترفع `.env.local` أو `.data` المحلية. لا تستخدم مجلد build مؤقتًا لتخزين المرضى والمرفقات.
5. نسخ `deploy/godaddy/environment.example` إلى `/etc/shorian/environment` بصلاحية 0640 وملكية root:shorian. لا تنسخ متغيرات تطبيق Next إلى المتصفح. الإعداد الافتراضي **عرض اصطناعي عام** وليس إطلاقًا للمرضى الحقيقيين.
6. نسخ `deploy/godaddy/shorian.service` إلى `/etc/systemd/system/shorian.service`، ثم `sudo systemctl daemon-reload` و`sudo systemctl enable --now shorian`. هذا يشغّل التهيئة ثم Next بعملية واحدة، والمنفذ 3000 مرتبط بـ127.0.0.1 فقط. تأكد أن مستخدم shorian يستطيع قراءة الكود وnode_modules ومخرجات البناء.
7. التأكد محليًا من `curl --fail http://127.0.0.1:3000/api/health` وأن `status` يساوي `ready`. فشل التهيئة يمنع بدء خادم التطبيق. عند خطأ القفل راجع العملية المالكة؛ لا تحذف ملف القفل بينما العملية تعمل.
8. في DNS لدى GoDaddy أضف/عدّل **A record للنطاق الفرعي المختار فقط** ليشير إلى IP الخادم. مثال: `clinic` ليصبح `clinic.yourdomain.com`. راجع السجلات الحالية أولًا؛ لا تستبدل الموقع الرئيسي أو MX/TXT للبريد. لا تضف AAAA إلا إذا كانت IPv6 مهيأة فعلًا.
9. استبدال `clinic.example.com` بالنطاق الحقيقي في نسخة Caddyfile. إن كان Apache/Nginx/لوحة إدارة يستخدم 80/443 فلا تثبّت Caddy فوقه ولا توقفه عشوائيًا؛ استخدم reverse proxy القائم أو اختر خادمًا مخصصًا بعد الفحص. يجب أن يحافظ الوكيل على Host الخارجي لفحص CSRF.
10. التحقق من Caddy config بـ`caddy validate --config <path>` قبل التفعيل. بعد إصدار الشهادة واكتمال DNS، اختبر `/api/health` عبر HTTPS وتسجيل الدخول والحجز والتحصيل والمرفقات. تأكد من Secure cookie عبر HTTPS، ثم أعد تشغيل الخدمة واختبر استمرار البيانات.

ملفات systemd تعمل بقيود نظام ملفات: التطبيق يكتب في `/var/lib/shorian` فقط، إضافة إلى مجلد tmp الخاص. إن أُضيفت لاحقًا ميزات تحتاج كتابة `.next/cache` فحدد مجلد cache منفصلًا بدل منح الكتابة إلى الكود كله.

## التحديث والنسخ

أوقف الخدمة قبل تشغيل migration أو backup أو إعادة البناء في checkout نفسه. احفظ نسخة من PostgreSQL **والمرفقات** باتباع README، ثم ابنِ النسخة الجديدة وأعد تشغيل الخدمة وافحص HTTPS. إعادة نسخة الكود وحدها لا تعكس migration لقاعدة البيانات؛ لا تُجرِ downgrade للقاعدة دون خطة استعادة مختبرة. النسخ خارج الخادم والاحتفاظ ومراقبة الخدمة لا تزال تحتاج إعدادًا فعليًا.

تعطيل DEMO_MODE وحده لا يجعل التطبيق جاهزًا للإنتاج. راجع `docs/VALIDATION.md` قبل استخدام أي بيانات طبية حقيقية.

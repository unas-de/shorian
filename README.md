# شُريان — Shorian

نسخة تطوير تشغيلية لإدارة يوم العيادة، عربية افتراضيًا. البيانات **محفوظة فعليًا** في PostgreSQL محلي عبر PGlite؛ لا تُخزن الملفات الطبية في localStorage. بيئة العرض تستخدم بيانات اصطناعية فقط وليست نظامًا جاهزًا لبيانات مرضى حقيقية.

## تشغيل سريع

المتطلبات: Node.js 24، npm. استخدم checkout الموجود؛ كل مهمة سحابية معزولة أصلًا ولا تحتاج Git worktree.

```bash
cd /workspace/shorian
npm ci
cp .env.example .env.local   # فقط إن لم يكن الملف موجودًا؛ لا تستبدل إعداداتك
npm run seed
npm run build
npm run start
```

الخادم يستمع على المنفذ 3000. للتطوير استخدم `npm run dev` بدل `start`. لا تشغّل خادمين أو seed أو النسخ الاحتياطي على قاعدة الملفات نفسها بالتزامن؛ يوجد قفل عملية يحميها. أوقف الخادم قبل التثبيت/الترحيل/النسخ. تعالج المهاجرات تلقائيًا عند أول فتح للقاعدة، داخل معاملات ومسجلة في `schema_migrations`.

- اختر «تجربة النظام» ثم العيادة والدور. هذا المدخل متاح **فقط** عند `DEMO_MODE=true`، وينشئ جلسة فعلية لعضوية حساب اصطناعي؛ ليس تبديلًا لصلاحية جلسة إنتاجية.
- عيادتان مستقلتان: النور والياسمين؛ لكل منهما مدير واستقبال وطبيب ومحاسب.
- حسابات البريد: `manager1@demo.shorian.local`، `receptionist1@demo.shorian.local`، `doctor1@demo.shorian.local`، `accountant1@demo.shorian.local`؛ استخدم 2 للعيادة الثانية.
- كلمات المرور مولدة عشوائيًا أثناء seed، محليًا في `.data/demo-credentials.txt` بصلاحية 0600. لا تُرفع إلى Git. مدير المنصة `platform@demo.shorian.local` وكلمة مروره في `.data/platform-credentials.txt`.
- لتدوير كلمات مرور الحسابات الاصطناعية فقط، والخادم متوقف: `npm run seed -- --rotate-demo-passwords`. لا توجد كلمات مرور إنتاجية ثابتة.
- تسجيل حساب جديد ينشئ عيادة وتجربة 14 يومًا. أضف طبيبًا وخدمة من الإعدادات قبل الحجز. التحقق من البريد واستعادته عبر البريد غير منفذين؛ توضح شاشة التسجيل ذلك.

## الرحلة المنفذة

مريض جديد ← حجز وخدمة وسعر ← وصول وقائمة انتظار ← بدء الكشف من حساب الطبيب ← مسودة محفوظة تلقائيًا مع version ووقت آخر حفظ ناجح ← اعتماد وقفل الزيارة ← ملحق تصحيح مؤرخ ← روشتة/ملخص عربي للطباعة وPDF من المتصفح ← دفع جزئي وكامل واسترداد ← تقرير مطابق للحركات.

تتوفر أيضًا إعادة الجدولة والإلغاء وعدم الحضور، اليوم/الأسبوع/الشهر، فلتر الطبيب، أوقات العمل وحجب الإجازات، أولوية انتظار بسبب مسجل، بحث محدود بالعيادة، ملفات مرضى وأرقام تلقائية، تطبيع الهاتف المصري وE.164 والتنبيه إلى الرقم المتكرر، تصدير ملف المريض حسب الدور، مرفقات PDF/PNG/JPEG خاصة، خصومات للمدير بسبب مسجل، مصروفات، وردية نقدية، إعداد خدمات وفريق، تقارير يومية وشهرية وCSV، وباقات وحدود مفروضة على الخادم وقاعدة البيانات. المدير الطبي ليس صلاحية ضمنية للمالك.

التحديث بين الأجهزة/الحسابات يتم باستطلاع الخادم كل 10 ثوانٍ؛ ليس Supabase Realtime. تعرض أخطاء الشبكة والحفظ دون ادعاء نجاح. لا يقترح التطبيق تشخيصًا أو جرعة أو تداخلات دوائية.

## قرار قاعدة البيانات والأمان

لم تكن مفاتيح Supabase أو خدمة PostgreSQL خارجية متاحة. استُخدم PGlite (PostgreSQL داخل عملية Node، مع مجلد بيانات دائم) لتوفير تشغيل فعلي وSQL وRLS دون مفاتيح. هذا **تشغيل بعملية واحدة وقرص دائم**، وليس بديلًا مثبتًا للنشر متعدد النسخ/Serverless. للمزيد: [البنية والصلاحيات](docs/ARCHITECTURE.md).

- الجلسات عشوائية، تُخزن بصمتها فقط في القاعدة، Cookie من نوع HttpOnly وSameSite=Lax، 12 ساعة. `SESSION_SECURE=true` يتطلب HTTPS.
- كلمات المرور scrypt بملح عشوائي. حد لمحاولات الدخول محليًا لكل بريد؛ يلزم حد موزع وسياسة MFA للإنتاج.
- الخادم يستخرج العضوية من الجلسة. اختيار العيادة لا يغير الدور. كل عملية أعمال تعمل داخل transaction مع `SET LOCAL ROLE clinic_app` وسياق مستخدم/عيادة وRLS. الدور محدود ولا يصل إلى profiles أو sessions.
- العلاقات المركبة `(clinic_id,id)` تمنع ربط عيادات مختلفة؛ تعارض الحجز وقيود ساعات العمل وحدود الباقة والمبالغ لها قيود/Triggers في القاعدة. قفل معاملات واستقلال السجلات الطبية والمالية.
- المرفقات في `.data/private-attachments` خارج public؛ حد 5 MiB للملف و100 MiB للعيادة محليًا، فحص ترويسة النوع، أسماء عشوائية، وروابط خمس دقائق مرتبطة بالمستخدم والعيادة تتطلب جلسة وصلاحية طبية عند كل تنزيل. ليس هناك تخزين سحابي أو فحص فيروسات مربوط.
- دفتر الدفع والاسترداد غير قابل للتعديل/المحو لدور التطبيق، ومفاتيح idempotency تمنع التكرار. الأموال أعداد صحيحة بأصغر وحدة نقدية، والإجماليات من الخادم.
- لا يوجد مفتاح service في المتصفح. أسرار التوقيع محلية غير متتبعة. لا توجد cache مشتركة لبيانات العيادات.

## الاختبارات

```bash
npm run typecheck
npm test
npm run build
# مع خادم شغال وDEMO_MODE=true، بيانات الاختبار اصطناعية وتبقى في قاعدة العرض:
node scripts/http-check.mjs
# يتطلب Chromium محليًا وpdftotext؛ TEST_DAY من نتيجة اختبار HTTP السابق:
TEST_DAY=2028-04-20 node scripts/browser-check.mjs
```

يمكن ضبط `CHROMIUM_PATH` و`APP_URL` لفحص HTTP. الاختبارات المباشرة تستخدم قاعدة مؤقتة مستقلة، ولا تستبدل بيانات العرض. صور المتصفح وPDF في `/tmp/shorian-review` وليست معاينة ويب منشورة. اطلع على [نتائج التحقق وحدود التنفيذ](docs/VALIDATION.md).

## النسخ الاحتياطي والاستعادة

**أوقف الخادم أولًا.** لا تنسخ مجلد PostgreSQL المفتوح بالنسخ العادي.

```bash
node --import tsx scripts/backup.ts create /tmp/shorian-backup-2026-10-30
node --import tsx scripts/backup.ts restore /tmp/shorian-backup-2026-10-30 /tmp/shorian-restored
```

النسخة تحتوي dump لمجلد PostgreSQL والمرفقات المشار إليها في القاعدة وmanifest ببصمات SHA-256. الاستعادة تتحقق من البصمات وتبني مجلدًا جديدًا، وترفض استبدال مجلد موجود. اختُبرت استعادة المرضى والمحتوى الطبي والمرفقات إلى قاعدة مستقلة. هذا ليس جدولة نسخ أو خطة تعافٍ إنتاجية. احتفظ بنسخ مشفرة خارج الجهاز، واختبرها دوريًا؛ اضبط الاحتفاظ ومتطلبات بلد التشغيل قبل بيانات حقيقية. مفتاح توقيع روابط الملفات ليس ضمن النسخة؛ يمكن توليد بديل بعد الاستعادة لأن الروابط قصيرة العمر. الجلسات ضمن snapshot تنتهي تلقائيًا؛ ألغها عند تعافٍ أمني.

## النشر وما يلزم قبل الإنتاج

هذه النسخة لا تدّعي استيفاء كل المتطلبات الموسعة. استخدم قرصًا دائمًا وخادم Node واحدًا للتقييم فقط، واضبط HTTPS و`SESSION_SECURE=true`. **عطّل DEMO_MODE قبل أي بيانات فعلية**، ولا تنقل seed الاصطناعي إلى تشغيل مرضى حقيقيين. لا تنشرها على بيئة قرص مؤقت أو عدة نسخ تشترك في ملفات PGlite.

التشغيل الإنتاجي يحتاج ربط PostgreSQL/Supabase وتعديل طبقة الاتصال واختبار RLS على الخدمة، وربط Auth للتحقق من البريد والاستعادة والدعوات وMFA، وتخزين خاص مع فحص ملفات ونسخ خارجية، ومراجعة أمان وامتثال/احتفاظ، واختبار أحمال وتزامن على PostgreSQL خارجي. تغيير `DATABASE_PATH` وحده لا يربط Supabase.

الدفع والرسائل تظهر «غير مربوط». العقود البرمجية في `lib/adapters.ts` تفشل صراحة حتى يتوفر مزود فعلي. لا Checkout وهمي، ولا Webhooks فعالة، ولا وسم إرسال/تسليم وهمي. يجب تنفيذ وتحقق توقيع وإزالة تكرار وترتيب أحداث مزود الدفع واختبارها عند اختياره. إدارة الاشتراك اليدوية موجودة؛ فواتير اشتراك المنصة منفصلة في schema لكن دورة إصدار/تجديد آلية كاملة غير منفذة.

اقرأ قائمة المتبقي كاملة في [VALIDATION.md](docs/VALIDATION.md). الفروع والتأمين والمخزون وبوابة المرضى والمعامل خارج الإصدار الأساسي.
